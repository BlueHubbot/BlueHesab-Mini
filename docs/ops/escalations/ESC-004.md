## Question
The `integration_test` step of `.github/workflows/spike-share.yml` failed for the third time on the same problem (flutter tooling reaching the emulator), so CB-1 stops a fourth variant. Should T-014 (a) add a device-recovery step and retry, (b) move the on-device clipboard test to a non-blocking job, or (c) keep it blocking and accept re-runs?

- Rules: AUTONOMY_AND_ESCALATION §7 CB-1, SPIKE_PLAN "Failure handling", T-014 acceptance criterion 5.
## Options
A) Before each attempt: `adb kill-server`/`start-server`, `adb wait-for-device` with a time limit and `sys.boot_completed`; on failure print `adb devices` and the emulator log tail. Cost: small; risk: hides a real emulator crash only if the log is not read.
B) Split the clipboard test into its own job with `continue-on-error`, keep share cases blocking. Cost: small; risk: a real clipboard regression would not block (spike only).
C) No change; re-run on failure. Cost: none; risk: red PRs and noise every run.
## Recommendation
A, with the diagnostics, because the failure is the emulator dropping off adb (seen in `ff28a4f`), which A addresses directly and B would only hide.
