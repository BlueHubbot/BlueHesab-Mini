## Understanding summary (AG-06) — written by the owner of the task before work starts
Written by Product/Contracts (same run). MX-08 says app_motion builds every controller and, in debug and test, registers it with the `BuildContext` that built it in a `MotionRegistry`; MotionProbe (`test/support/motion_probe.dart`) reads only that registry and never advances time. So this slice adds (1) `MotionProperty` (`opacity`, `dx`, `dy`, `scale`, `progress`); (2) `MotionHandle`, the one way to get an `AnimationController` for a table 4-3 row phase: it resolves the phase with RM-02 (`resolveMotion`), owns the controller, registers it (debug/test only, inside `assert`), lets the widget `track` which property each animation drives, and plays it (`forward`/`reverse` show the end state at once when the resolved phase does not animate; `repeat` only for a loop phase that still loops); (3) `MotionRegistry`, read-only to everyone but `MotionHandle`; (4) MotionProbe with `activeCount(Finder subtree)`, `activeLoopCount(Finder subtree)` and `value(Finder target, MotionProperty property)`, no tolerance of its own.
Spec tension found while reading: MX-08 says that with reduced motion "the non-loop count must be zero and the value is the end value from the first frame", while RM-02 (and MX-02) keep a crossfade of `exit` for rows marked «محو» and run «همان» rows unchanged. Raised as ESC-009 (D2, non-blocking). Conservative default (AG-16): the merged RM-02 resolution (T-037) stands; MotionProbe only reports what runs and decides nothing, so it does not depend on the answer; the tests assert MX-08's zero-count sentence only for «آنی» and «ایستا» rows.

## Objective
A widget test can build an animated widget through `MotionHandle`, advance time with `tester.pump(Duration)`, and ask MotionProbe how many non-loop and loop animations run in a subtree and what opacity/offset/scale/progress the target has, with and without reduced motion.
