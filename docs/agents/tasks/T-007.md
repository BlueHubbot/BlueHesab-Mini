## Understanding summary (AG-06) — written by the owner of the task before work starts
Written by Builder-Domain (scheduled run), 2026-10-30. Prove in a new spike package `spike/T-007-timezone/` that one small time-zone layer over `package:timezone` 0.11.2 gives what the data model needs: instants stored as ISO-8601 UTC with milliseconds (DT-A), "today" as a Gregorian `yyyy-MM-dd` computed in an IANA zone from an injected UTC clock (DT-C, SD-06: the layer never reads the clock), and offsets and DST that come only from the tz database (DT-02). Check the package's offsets against an independent reference (Python `zoneinfo` over the system IANA database, written as Dart source so the same test runs in Chrome), check `Asia/Tehran` explicitly, and verify the audit row's open items: no `package:http` in the import closure the app would use (T-07), data variant sizes, and the embedded data version. Interpretations (D0): (1) a separate spike package instead of extending `spike/T-004-jalali/`, so that lockfile and its review stay unchanged; (2) only the `latest` data variant is used and cross-checked; sizes of all variants are recorded; (3) local wall times that do not exist or exist twice (DST gap/overlap) have no rule ID: the spike records what the package does and decides nothing; (4) the device's own IANA zone (default of `app.timezone`) cannot be read without a platform plugin that has no audit row: recorded as a finding, not solved.

## Objective
Close the timezone half of SP-04: a central zone layer with DT-A formatting/parsing and DT-C "today", offsets equal to an independent IANA reference on 2000…2035 for 7 zones, `http` absent from the used import closure, all on Linux, macOS, Windows and Chrome.

## Non-goals
Reading the device time zone (needs a plugin and an audit row), reminders or scheduled times, Jalali display of instants (T-004 layer), user-facing strings, `lib/**`, choosing between `latest` / `latest_10y` / `latest_all` for the product (proposal only).

## Acceptance criteria
- [ ] DT-A: `formatInstant` gives `2026-10-24T06:55:00.000Z` style output (UTC, exactly 3 fraction digits, microseconds truncated, local input converted); `parseInstant` accepts only that shape and round-trips. Evidence: CI test log.
- [ ] DT-C: `todayIn('Asia/Tehran', now)` is `2026-10-29` at `2026-10-29T20:29:59.999Z` and `2026-10-30` at `20:30:00.000Z`; same boundary checks for one DST zone on both sides of a transition. Evidence: CI test log.
- [ ] DT-02: for `Asia/Tehran`, `Asia/Dubai`, `Asia/Kabul`, `Europe/Berlin`, `Europe/London`, `America/New_York`, `Australia/Sydney`, every offset change 2000-01-01…2036-01-01 of the reference is seen by the package at the same second (offset before at t−1 s, after at t), and two samples per year agree. `Asia/Tehran`: +04:30 in July 2022, +03:30 in July 2023 and later. Evidence: CI test log, VM and Chrome.
- [ ] T-07: the import closure of the spike library (following `import`/`export`/`part`, including every conditional URI) contains no `package:http`; the files of `timezone` that do import it are listed. Evidence: CI test log / evidence line.
- [ ] Data: package version, data variant files and their sizes recorded; DST gap/overlap behaviour of `TZDateTime` recorded (no decision). Evidence: evidence line, README.
- [ ] Analyzer clean, license scan 0 failing on the new lockfile (`timezone` and its graph), tests green on Linux, macOS, Windows, Chrome; README with findings. Evidence: CI output pasted in the PR.
