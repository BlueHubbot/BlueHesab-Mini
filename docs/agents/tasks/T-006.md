## Understanding summary (AG-06) — written by the owner of the task before work starts
Written by Builder-Domain (scheduled run), 2026-10-29. In `spike/money/`, prove two things T-002 did not: (1) two connections to one database file in one process (drift background isolates, as a UI isolate and an export/backup isolate would be) behave as SQLite WAL promises: a read transaction is a stable snapshot while the other connection commits, a second writer waits for the first with `busy_timeout` and fails fast without it, a rolled-back write is never seen, and a read transaction that later tries to write after another commit fails even with `busy_timeout` (so the product needs one writer or `BEGIN IMMEDIATE`); after the last connection closes no `-wal` file is left, so the MG-02 recovery copy still works; (2) a backup written by the older schema (v1, made from the frozen v1 fixture through the v1 code) restores into a v2 database by BACKUP_RESTORE §4 step 7: validate against the v1 field set, apply into a staging database at v1, run the same MG-01 migrations, check integrity, then copy into the target in one transaction; any failure leaves the target unchanged and no staging file behind. Interpretations (D0): (a) the staging database reuses the SQL migrations instead of a second JSON upgrade path, so one migration list stays the source of truth; (b) the field set of a backup follows its `schema_version` (v1 has no `external_ref`), and a v1 file carrying a v2 field is rejected; (c) restore still needs an empty target in the spike (replace = clear + insert is product work).

## Acceptance criteria
- [x] Both connections report `journal_mode = wal`; a read transaction sees the same counts before and after the other connection commits, and the new rows after it ends. Evidence: CI test log per OS.
- [x] Writer/writer: with `busy_timeout = 0` the second writer fails with "database is locked" and nothing of it is stored; the second write gets in after the first commit and both rows exist. Deviation (finding 12 in the README): SQLite's own wait works on macOS/Windows but gives up after ~64 ms on Linux, so the test uses a Dart-side retry and records the engine wait per OS. Evidence: CI test log.
- [x] A rolled-back transaction on one connection is never visible to the other; a read-then-write transaction after the other connection committed fails even with `busy_timeout` (recorded as a finding for ADR-0003). Also found: drift `transaction()` takes the write lock at its start, so snapshot reads use a manual `BEGIN DEFERRED` (finding 11). Evidence: CI test log.
- [x] After both connections close no `-wal` file is left and `copyForRecovery` (MG-02) works; while a WAL connection is open it refuses. Evidence: CI test log.
- [x] A v1 backup exported by the v1 code from the frozen fixture has `schema_version` 1 and no `external_ref`; it restores into an empty v2 database (18-digit amount, 1, negative opening balance and the Persian name with ZWNJ exact; `external_ref` null; target stays v2 with history [1, 2]); re-export is a valid v2 backup with the same logical data. Evidence: CI test log.
- [x] Rejections leave the target unchanged and no staging file: non-empty target, a v1 file with a v2 field, a newer-schema file (MG-03). Evidence: CI test log.
- [x] Analyzer clean, no-float check green, license scan 0 failing (lockfile unchanged), all on Linux, macOS, Windows; README updated with SP-05 findings. Evidence: CI output pasted in the PR.
