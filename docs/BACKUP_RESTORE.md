# Backup and Restore (v2)

**Status:** PROPOSED · **Owner:** Builder-Domain (Agent 3) · **Date:** 2026-10-26 · Data contract: `docs/architecture/DATA_MODEL.md` §10; requirements CORE-004; invariants I-09, I-10; scope F11.

## خلاصه‌ی فارسی
پشتیبان یک فایل JSON است که خودتان در جای دلخواه ذخیره می‌کنید (بدون ابر). بازیابی اول فایل را کامل بررسی می‌کند، قبل از هر تغییر یک نقطه‌ی بازگشت می‌سازد و فایل خراب را بدون هیچ تغییری رد می‌کند. در v0.1 جایگزینی کامل است؛ ادغام بعداً.

## 1. Goals and non-goals
Portable backup between devices/OSes; no cloud; no silent overwrite; versioned; testable. Non-goals v0.1: scheduled/automatic cloud backup, merge restore, sync, per-record import.

## 2. File format
- Extension `.bluehesab` (content is UTF-8 JSON; optionally gzip later). Top-level: `format: "bluehesab-backup"`, `format_version` (integer, starts 1), `schema_version` (DB version), `app_version`, `exported_at` (UTC), `device_label` (optional, user-editable, default empty), `counts` per entity, entity arrays, `checksum` (sha256 of canonical body without the checksum field).
- Entities: accounts, account_hints, categories, capture_merchant_map, transactions, budget_limits (module section), settings. Soft-deleted rows and idempotency rows excluded.
- Money = decimal strings; dates/instants as in DATA_MODEL; canonical JSON (sorted keys, no whitespace) for hashing.
- Never included: raw SMS, images, secrets/tokens (model endpoint token), logs.
- v0.1 is **unencrypted**; the UI says so plainly at export (CAPTION: «این فایل رمزگذاری نشده است»). Encrypted export (passphrase, authenticated encryption, key-derivation parameters in header) is v0.2 candidate; no encryption claim until designed and tested (SECURITY_PRIVACY_MODEL).

## 3. Export flow
1. User opens Settings › Backup › «ساخت پشتیبان».
2. App takes a consistent snapshot (single read transaction), builds JSON in a background isolate, writes to the platform save dialog / share sheet (Android: SAF or share; desktop: save dialog).
3. Result screen: file name `bluehesab-YYYYMMDD-HHmm.bluehesab`, counts, size, checksum prefix, reminder to keep it somewhere safe. Records `last_backup_at` (setting).
4. Failure (disk full, cancelled) leaves no partial file where possible; error is specific and recoverable.

## 4. Restore flow (replace)
1. User picks a file. Size cap (e.g. 200 MB) before reading.
2. **Validate, change nothing:** JSON parse; `format` and `format_version` known; `schema_version` ≤ app supported (else reject, MG-03); counts match; checksum matches; referential integrity (every transaction's account/category exists; transfers valid; currency consistency DD-04); amounts match the money pattern and ≤ 18 digits; dates valid.
3. **Preview:** show counts, date range, exported_at, device_label and consequences: «همه‌ی داده‌های فعلی جایگزین می‌شود».
4. Confirmation dialog (destructive style, explicit button; no default focus on it).
5. **Recovery point:** copy current DB file to the recovery slot (keep last 3, same mechanism as MG-02) *before* writing.
6. Apply in one DB transaction (clear + insert); on any error roll back and keep the old data.
7. Run migrations if backup `schema_version` < current; re-run integrity checks; rebuild caches.
8. Report: success counts, or failure reason; offer «بازگشت به نقطه‌ی قبل» for 7 days, as long as that recovery point is still among the last 3 kept.
Malformed, truncated, wrong-checksum, newer-version files are rejected with a specific message and **zero** change (I-10).

## 5. Compatibility policy
Newer app reads older `format_version` (migrates on load). Older app rejects newer. `format_version` bumps only on structure change; documented in CHANGELOG and release notes. Cross-platform portability is tested (Android↔Windows↔macOS) before it is claimed.

## 6. Tests (TEST_STRATEGY)
Round trip equal logical data (I-09, canonical hash); 18-digit amounts; Persian text/ZWNJ preserved; empty database; 20k transactions within time budget; each rejection case; recovery-point restore; interrupted restore (kill process) leaves old data; backup from module-off state restores module data; fixtures generated by script, never real data.
